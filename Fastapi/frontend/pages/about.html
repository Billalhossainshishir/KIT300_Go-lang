THE PROBLEM

The problem in simple terms

Shopping is starting to happen without us. You ask for something, software finds it, and increasingly that software can complete the purchase on its own. Which raises a question nobody used to have to ask out loud: how does it know the thing is genuine?

A language model can be useful for understanding a request and explaining a result, but product trust should not depend on generated language alone. A confident explanation is not the same thing as verified evidence.

That is fine when you are asking for a recipe. It is not fine when the product is a batch of examination gloves that was recalled last month, or a supplement whose lab certificate expired in April, or a listing from a seller nobody has ever verified.

WHAT RAMIFY OS DOES ABOUT IT

Seven checks, the same way every time

It separates interpretation from product assessment. The model can help understand the request, while deterministic checks evaluate the product facts. They give the same answer every time, from the same evidence, no matter who is asking.

  1. 01Is this the product it claims to be?
  2. 02Is there a recall or advisory against this batch?
  3. 03Is the seller established for this category?
  4. 04Is the paperwork this category requires attached?
  5. 05Is that paperwork still in date?
  6. 06Do the claims come from bodies entitled to make them?
  7. 07Do any two sources contradict each other?
The language model explains the decision. It does not make it.

TWO QUESTIONS, NOT ONE

Two questions, not one

Is this product sound?

That is a question about the product. It has one answer, and everybody gets the same one.

May this buyer act on it?

That is a question about you. Your spending limit, your approved brands, your suppliers, whether you want to see anything carrying a warning before it goes through.

Your own rules can make an outcome stricter; an agent may always stop on something the checks passed. They cannot make it looser. There is no combination of settings that turns a recall into a purchase, for any agent, including one you build yourself.

WHAT YOU GET BACK

Three answers, and only three

Green

A clean approval. The checks are satisfied and no warning is attached.

Orange

Attention is required: an approved result with a warning, or a genuine pause for human review. The label and receipt always say which one; colour alone is never the decision.

Red

Something failed on grounds no setting can wave through. Your agent will not proceed, and neither will anybody else's.

Underneath, the system works in five outcomes rather than three, because "allowed, with something you should read" and "allowed" are genuinely different, and so are "stopped on a finding" and "stopped because there was not enough on file to judge". The receipt carries the precise one. The colour is only ever how it is shown to you, and is never stored.

RECEIPTS

And receipts people can actually read

Every check produces a machine receipt: what was looked at, what was found, what was decided, and when. If a person later decides a reviewable case, the system creates a linked Human Receipt that explains the same record in plain English and keeps the full JSON underneath. Both are sealed when they are written: a SHA-256 hash of the exact bytes, and a system Ed25519 signature over that hash, so if a single character changes later, checking it says so.

Not that the file cannot be edited. Anyone can edit a file. That it cannot be edited without the change being obvious. That is a smaller promise, and it is one that can actually be kept.

WHY IT IS AUDITABLE

Why the design is auditable

The product result is separate from the buyer

Everyone gets the same answer about the product. What differs is only what each buyer may do with it, written into the receipt as its own field.

Missing information is shown as missing

Missing evidence is not evidence of a problem. When there is not enough on file to judge, the answer says so and the agent stops.

The receipt can be checked

By you, an accountant or a regulator, on another computer, months later. The interface button and the command-line tool run the same code.

Human decisions are recorded separately

A person may decline or authorise once. That choice gets its own sealed Human Receipt; the original is left exactly as it was. Hard stops such as recall never enter review.

Agent settings cannot remove hard stops

You can let an agent spend more or act without asking. You cannot tell it a recalled product is fine.

SCOPE

What this demo includes

A prototype built for the University of Tasmania's KIT300 capstone. The documented configuration binds the application to the local machine, and the optional model connection is directed to local Ollama. This describes the configured architecture rather than claiming to prove network isolation.

Twelve products across two categories from five sellers, with twenty evidence records issued by three laboratories and regulators, and seventeen named cases. Every date is judged against a fixed snapshot of 24 July 2026, so a case that returns a warning today still returns it next year.

The honesty boundary. The products, brands, sellers, laboratories, certificates and prices are invented and certify nothing. The cryptography is not invented: every hash is a genuine SHA-256 digest and every signature a genuine Ed25519 signature. What is small here is the size of the catalogue, not the honesty of what runs over it.
